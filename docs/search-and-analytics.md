# Поисковики и статистика

## Состояние

Полная HTML-сборка создаёт 14 страниц и отдельный `404.html`; содержимое есть до исполнения JavaScript. Метаданные, canonical, Organization/WebSite/WebPage/BreadcrumbList JSON-LD берутся из одного реестра. Детали услуг остаются заглушками с `noindex,follow`, без выдуманных услуг, отзывов, рейтингов и цен в JSON-LD. Sitemap содержит только разрешённые индексируемые страницы.

Основные адреса `/about/`, `/services/`, `/contacts/` уже смысловые. Для услуг `slug` теперь отделён от постоянного `id`; история адресов хранится в `aliases`. После утверждения названия изменить slug, добавить прежний slug в aliases. Генератор проверит пересечения, обновит ссылки, canonical и JSON-LD, создаст 301 для Apache и Vercel. До появления названий адреса `service-01`…`service-08` сохранены: заменять их произвольными услугами нельзя.

## Что нужно владельцу для отправки sitemap

Данные REG.RU/Vercel/GitHub не заменяют подтверждение сайта в кабинетах поисковиков. На момент реализации кабинеты и их доступы не предоставлены; **фактическая отправка sitemap не выполнена**.

1. Войти в [Google Search Console](https://search.google.com/search-console/), добавить доменный ресурс `xn--80abmkm6an.xn--p1ai` (трибека.рф).
2. Скопировать **выданную Google** TXT-запись. В REG.RU открыть управление DNS домена, добавить TXT в корень домена, не менять существующие MX/A-записи. Значение записи уникально; его нельзя придумать заранее. Если DNS обслуживается другим провайдером, добавить запись у него.
3. Вернуться в Search Console и нажать подтверждение. Открыть Sitemaps и отправить `https://xn--80abmkm6an.xn--p1ai/sitemap.xml` после публикации проверенной сборки.
4. Войти в [Яндекс Вебмастер](https://webmaster.yandex.ru/), добавить HTTPS-сайт без www, выбрать подтверждение DNS TXT, добавить именно выданную Яндексом запись и подтвердить права. В разделе индексирования / Sitemap добавить тот же адрес.
5. Сохранить статус принятого файла в обоих кабинетах. Принятие sitemap не гарантирует индексацию каждой страницы.

Google прекратил поддержку старого неавторизованного sitemap ping: [официальное сообщение](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping). Ссылка Sitemap в robots.txt обеспечивает обнаружение, но не является подтверждением отправки через кабинет.

Для последующей автоматизации подготовлен `npm run sitemap:submit`: по умолчанию только показывает план без сетевых запросов. `npm run sitemap:submit -- --submit` использует авторизованные [Google Sitemaps API](https://developers.google.com/webmaster-tools/v1/sitemaps/submit) и [Яндекс API](https://www.yandex.ru/dev/webmaster/doc/ru/reference/host-user-added-sitemaps-post). Не помещать токены в `VITE_*` или Git. Серверные переменные: `GOOGLE_SEARCH_CONSOLE_TOKEN`, `GOOGLE_SEARCH_CONSOLE_PROPERTY` (например `sc-domain:xn--80abmkm6an.xn--p1ai`), `YANDEX_WEBMASTER_TOKEN`, `YANDEX_WEBMASTER_USER_ID`, `YANDEX_WEBMASTER_HOST_ID`. При отсутствии доступа команда явно сообщает NOT submitted и заканчивается ошибкой.

## Добровольная аналитика

Аналитика собственная, без стороннего счётчика. По умолчанию отключена. В подвале «Настройки статистики» посетитель включает и отзывает разрешение; выбор хранится в localStorage. DNT/GPC имеют приоритет над разрешением. Это отдельный выбор от согласия на обработку заявки. Встроенная карта Яндекса сохранена и работает отдельно.

| Событие | Момент |
| --- | --- |
| `page_view` | Просмотр страницы после разрешения |
| `form_start` | Первое взаимодействие с формой |
| `form_submit` | Только подтверждённое сервером успешное принятие |
| `phone_click`, `email_click` | Нажатие на телефон / почту |
| `messenger_click` | WhatsApp, Telegram, MAX |
| `service_click` | Переход в карточку услуги |

Передаются только известный путь и разрешённые категории. Имя, телефон, текст формы, файлы, referrer, query string, идентификатор заявки и посетителя отсутствуют в payload. Неизвестные URL заменяются `/404/`. `utm_source` и `utm_medium` ограничены известными категориями, неизвестные значения становятся `other`. `utm_campaign` сохраняет только заранее разрешённые коды из `VITE_ANALYTICS_CAMPAIGNS` и **такого же** списка `analytics_campaigns` в закрытом PHP config. Пока кодов нет, кампании группируются как `other`; `utm_term`/`utm_content` не сохраняются, поскольку часто содержат свободный текст. Атрибуция начинается после разрешения и живёт в памяти вкладки, без межвизитного объединения.

На REG.RU `/api/analytics.php` сохраняет дневные суммы в закрытый `analytics_dir`, файл 600, каталог 700. Нет отдельных событий/профилей посетителей, IP и User-Agent в статистике. IP применяется отдельно для короткого технического rate limit; технические журналы веб-сервера регулируются настройками хостинга. Ограничения события/размера/категорий проверяются также PHP, сумма изменяется под flock с атомарной заменой JSON. Backup берёт общую maintenance-блокировку. Это суммы действий, **не уникальные посетители**. Повтор одного типа события с одного адреса в пределах секунды ограничивается от спама.

По умолчанию аналитика preview идёт на собственный origin Vercel, где API исключён, поэтому просмотр разработки не загрязняет production. Для выделенного тестового PHP backend можно задать `VITE_ANALYTICS_ENDPOINT` и точный origin в config.
