# Статические страницы и SEO

`npm run build` собирает клиентский JavaScript, затем запускает `scripts/generate-seo-pages.mjs`. Этот скрипт собирает временный серверный модуль Vite, вызывает `renderToString` для каждой страницы и удаляет временный модуль. На хостинге Node.js не нужен: используются обычные HTML/CSS/JS и существующий PHP API.

Первый HTTP-ответ содержит полноценные заголовки, тексты, карточки услуг, ссылки, форму и нижнюю мобильную навигацию. При загрузке JavaScript React гидратирует эту разметку. Если общий `404.html` обслуживает произвольный неизвестный адрес, клиент заново рисует страницу ошибки, чтобы избежать расхождений при гидратации.

Проверки:

```sh
npm run build
node scripts/verify-prerender.mjs
npm test
```

В `dist/prerender-manifest.json` перечислены все 14 страниц и отдельная страница ошибки. `verify-prerender.mjs` читает готовый HTML без исполнения JavaScript, проверяет содержимое, H1, внутренние ссылки, форму, мобильную навигацию, JSON-LD и соответствие sitemap. HTTP-статус 404 задаётся конфигурацией хостинга; наличие файла `404.html` само по себе не задаёт статус.

## Адреса услуг

В `src/data/company.js` у услуги есть:

- `id` — постоянный внутренний ключ;
- `slug` — актуальный адрес страницы;
- `aliases` — предыдущие значения slug;
- `placeholder` — временный контент, закрытый от индексации.

Названия восьми услуг пока не предоставлены. Поэтому существующие `/services/service-01/` … `/services/service-08/` сохранены. Новые названия и производственные возможности не выдумывались. Пути основных разделов `/about/`, `/services/`, `/contacts/` уже описывают содержание.

После согласования названия задайте содержательный slug, оставьте `id` без изменений, а прежние описательные slug перенесите в `aliases`. Пример механики (это тестовые данные, а не утверждение о конкретной услуге компании):

```js
{
  id: 'service-01',
  slug: 'tokarnaya-obrabotka',
  aliases: ['tokarnye-raboty'],
  placeholder: false,
  // Утверждённые title, short, details…
}
```

Сборка создаст постоянные перенаправления со старого id и aliases на новый slug. Правила попадают в `dist/redirects.json`, Apache `.htaccess` и файл `_redirects`; подготовка Vercel использует тот же манифест. Совпадения и недопустимые символы в адресах останавливают сборку.

## Метаданные и индексирование

Каждая страница получает собственные title, description, canonical, Open Graph, Twitter и JSON-LD. В JSON-LD используются реквизиты из проекта: Organization, WebSite, WebPage и хлебные крошки; для контактов — ContactPage, для компании — AboutPage. Заглушкам не приписываются Service/Offer, цены, отзывы или рейтинги.

`sitemap.xml` включает только четыре индексируемых основных раздела. Юридические страницы, заглушки услуг и ошибки исключены. `robots.txt` сообщает адрес sitemap и запрещает обход API. `lastmod` не подменяется датой каждой сборки.

Публикация `robots.txt` даёт поисковикам возможность обнаружить sitemap. Подтверждённую отправку в кабинет необходимо учитывать отдельно: Google поддерживает Search Console/API, а устаревший ping возвращает 404 ([официальное объявление](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping)). Яндекс предоставляет [авторизованный API добавления sitemap](https://www.yandex.ru/dev/webmaster/doc/ru/reference/host-user-added-sitemaps-post). Для такой отправки нужен доступ владельца сайта или соответствующий API-токен; генерация файла не означает отправку и не гарантирует индексацию.
