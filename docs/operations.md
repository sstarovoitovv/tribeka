# Обслуживание

## Публикация

Workflow `.github/workflows/deploy-reg-ru.yml` собирает `main` и публикует отдельный релиз. Хост, расположение приложения, публичный каталог и PHP CLI задаются в workflow; закрытая серверная конфигурация в релиз не входит. Перед слиянием выполняется `npm run check` локально.

`server/deploy-release.php` проверяет комплектность релиза и PHP, создаёт согласованную резервную копию и атомарно переключает ссылку `current`. HTTP-проверка проверяет release marker, HTML, API OPTIONS, заголовки, 404 и перенаправления. При ошибке активируется rollback-релиз. Данные и схема БД при переключении не откатываются.

Публичный каталог должен быть ссылкой на `current/public`, а `current` — на каталог релиза. Первичная настройка этих ссылок выполняется администратором хостинга. Скрипт отказывается перезаписывать физический публичный каталог. Предыдущие хешированные JS/CSS включаются в новый релиз для открытых вкладок; их удаление требует отдельной политики хранения.

## Данные

Общая maintenance-блокировка согласует запись заявки, очистку и backup. Backup занимает эксклюзивную блокировку; новые записи получают временный `503` с `Retry-After`.

`server/backup-data.php` сохраняет SQL, вложения, конфигурацию и manifest с SHA-256 в закрытом каталоге. Незавершённая копия не публикуется. Настройки ротации: `backup_keep`, `backup_max_age_days`. Режим `--prune-only` выполняется ежедневно независимо от успеха новой копии.

`server/purge-expired-leads.php` удаляет просроченные заявки и их файлы. Задачи обслуживания должны обращаться к CLI-скриптам активного релиза. Удаление email-копий и досрочное удаление по обращению субъекта выполняются отдельно: очистка базы не удаляет письма.

## Восстановление

Используются SQL и вложения одного snapshot. Перед восстановлением проверяются manifest, SHA-256 и состав архивов. Проверка восстановления выполняется в отдельной БД и пустом закрытом каталоге. Конфигурация сравнивается с текущей, а не заменяется безусловно.

Production-восстановление требует остановки записи и обслуживания, сохранения текущего snapshot и согласования удалённых после backup данных. Резервная копия не должна возвращать ранее удалённые персональные данные в обработку.

Откат кода запускается через workflow с `rollback_id` существующего релиза либо через `deploy-release.php --rollback-id=...` с путями приложения, docroot и health URL. Локальная копия на сервере не является внешним disaster-recovery backup.
