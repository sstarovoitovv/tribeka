# Эксплуатация

## Публикация и откат

`.github/workflows/deploy-reg-ru.yml` собирает `main` и загружает отдельный релиз. Адрес сервера и пути заданы в workflow; закрытая конфигурация хранится отдельно. До слияния выполняется `npm run check` локально.

`server/deploy-release.php` проверяет комплектность и PHP, создаёт согласованный backup и атомарно переключает `current`. HTTP-проверка охватывает release marker, HTML, API OPTIONS, заголовки, 404 и redirects. При ошибке выполняется откат кода; БД не откатывается.

Структура сервера: `current → releases/<id>`, публичный каталог `→ current/public`. Публикация отказывается заменять физический публичный каталог. Старые хешированные JS/CSS сохраняются для открытых вкладок; их удаление требует отдельной политики хранения.

Для отката workflow принимает `rollback_id` существующего релиза. Тот же механизм доступен через `deploy-release.php --rollback-id=...` с путями приложения, docroot и health URL.

## Обслуживание данных

| Скрипт | Назначение |
| --- | --- |
| `server/backup-data.php` | SQL, вложения, конфигурация и manifest с SHA-256 в закрытом каталоге |
| `server/purge-expired-leads.php` | Удаление просроченных заявок и файлов |

Cron должен вызывать скрипты активного релиза. Backup удерживает эксклюзивную maintenance-блокировку; запись заявки временно получает `503`. Незавершённые копии не публикуются. Ротация задаётся `backup_keep` и `backup_max_age_days`; `--prune-only` выполняется ежедневно независимо от успешности новой копии.

Очистка БД не удаляет почтовые и рабочие копии. Хранение и организационные ограничения — в [personal-data.md](personal-data.md).

## Восстановление

Используются SQL и вложения одного snapshot с проверенным manifest и SHA-256. Сначала выполняется восстановление в отдельную БД и пустой закрытый каталог. Конфигурация сравнивается с текущей.

Восстановление production требует остановки записи и обслуживания, копии текущего состояния и учёта удалённых после backup данных. Локальная копия на том же сервере не защищает от утраты хостинга.
