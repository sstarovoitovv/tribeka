# Безопасность

## HTTP и браузер

Публичный PHP endpoint — `POST /api/request.php`; `OPTIONS` обслуживает CORS
preflight. Остальные PHP-пути и неизвестные URL завершаются HTTP 404. Правила
Apache в `public/.htaccess` также запрещают листинг каталогов и закрывают пути
к исходникам и служебным данным.

Сайт выставляет `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Permissions-Policy`, HSTS на один год и CSP. CSP разрешает фреймы Яндекс Карт;
скрипты и шрифты загружаются с сайта. CORS разрешает только настроенные origins.
`Origin` не используется как аутентификация: сервер проверяет данные заявки
отдельно от браузерных ограничений.

## Заявки и вложения

PHP проверяет UTF-8 и длину строк, нормализует телефон, требует согласие и
актуальные версии документов. В URL страницы-источника сохраняются только origin
и path — query string и fragment отбрасываются. Запись заявки и метаданных
вложений выполняется PDO prepared statements в одной транзакции; при ошибке БД
загруженные для этой заявки файлы удаляются.

Лимиты вложений: пять файлов, 15 MiB суммарно. Сервер проверяет статус HTTP-upload,
размер, расширение, MIME и сигнатуру файла. Файлам назначаются случайные имена;
они хранятся с ограниченными правами вне web root, не распаковываются и не имеют
публичных URL. Для каждого файла в БД сохраняется SHA-256. Проверка формата не
заменяет антивирусное сканирование. Подключение описано ниже.

## Ограничение запросов и обслуживание

Rate limit допускает одну попытку с IP-адреса за 30 секунд. Счётчик резервируется
атомарно через `flock` до проверки полей; превышение возвращает `429` и
`Retry-After`. Используется `REMOTE_ADDR`, заголовки `X-Forwarded-For` игнорируются.
Если перед Apache стоит proxy, его конфигурация должна передавать адрес клиента
только от доверенного proxy; иначе клиенты за общим адресом разделят лимит.
Ошибка чтения или записи состояния rate limit закрывает endpoint с `503`.

Обработчик заявки и очистка заявок держат shared maintenance lock; backup берёт
exclusive lock, чтобы согласовать копию MySQL и вложений. Пока backup удерживает
блокировку, новые заявки временно получают `503`.

## Проверки и эксплуатация

`npm run test:php` проверяет валидацию, согласие, вложения, запись и конкурентный
rate limit на изолированных данных. `npm run test:apache` проверяет rewrite и
правила доступа, если Apache доступен. Проверки не отправляют заявки в production.
Размещение серверной конфигурации, backup и восстановление описаны в
[operations.md](operations.md). Приёмка сервера дополнительно требует проверить
реальный IP за proxy и восстановление базы вместе с вложениями.

## Антивирусная проверка

`public/api/_lib/attachment-scanner.php` подключает ClamAV до перемещения файлов и записи в БД. Конфигурация `antivirus`: `enabled`, абсолютные `binary` и `database_dir`, `timeout_seconds` (1–120). Команда запускается массивом аргументов через `proc_open`, без shell. Все файлы одной заявки проверяются одним процессом.

При включении проверяются дата базы (не старше семи дней), код завершения и ограничение времени. Зашифрованные документы, превышение глубины/размера сканирования, макросы и повреждённые контейнеры настроены как отрицательный результат. Обнаружение угрозы возвращает `422`, недоступность или устаревшая база — `503`; сохранения и email при этом нет. Заявка без вложений не зависит от сканера.

Сканер подготовлен, но в production не активирован. Проверка 19.10.2026: база ClamAV на хостинге датирована 14.07.2021, работающего clamd нет, CDN обновления отвечает HTTP 403. До обновления базы и проверки ресурсов включение приведёт к отказу загрузок. Настройка не меняет доступность поддерживаемых форматов; зашифрованный архив нельзя признать проверенным.

Тесты проверяют границу запуска, вердикты, устаревшую базу и timeout через изолированный исполняемый fixture. Они не заменяют приёмку реального ClamAV с актуальной базой на целевом сервере.
